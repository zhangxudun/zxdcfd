# 第 8 步测试需求：判定与回退

> 对应 [工作流程](工作流程.md) 第 8 步和第 4 节。
> 产物：结论（返回值，不写文件）。通过条件：结论为“通过”；否则给出回到哪一步、怎么处理。
> 实现：`judge_result.py`。测试：`tests/test_judge_result.py`。

## 1. 范围

- 测：第 7 步全部通过时是否给出“通过”；检查不通过时回到哪一步是否与工作流程第 4 节一致；第 2–7 步报错时回到哪一步是否判对；多项不通过时是否逐项给出原因、步骤是否合并去重；`结果.json` 缺失、不完整或自相矛盾时是否报错而不是给结论；是否不改动任何文件、不重跑任何步骤；命令行返回值是否能直接用于 CI。
- 不测：六项检查的阈值和算法（第 7 步）、日志和监测数据的判定（第 6 步）、各步骤自己的报错条件（第 2–6 步）。
- 第 8 步只判定，不返工：不改标注、不改网格尺寸、不改步数，不调用第 1–7 步，不运行 OpenFOAM。返工由人或上层脚本按结论去做。
- 结局分三种，测试要分清：
  - 通过：不报错，结论为“通过”，没有要回到的步骤。
  - 返工：不报错，结论为“返工”，每个原因都写明回到哪一步、怎么处理。
  - 不能判定：输入不是第 7 步的结果，也不是第 2–7 步的报错，或者 `结果.json` 不可信。报错，不给结论。
- 测试点分三类：“造数”类由测试自己写 `结果.json` 或结果字典，不需要先跑前面的步骤；“触发”类真的调用第 2–7 步的函数让它报错，再把异常交给第 8 步，不需要 OpenFOAM；“OF”类真的从第 2 步跑到第 7 步。回退规则都放在“造数”和“触发”类里测。

## 2. 测试输入与约定

### 2.1 基准结果 R0（“造数”类）

测试在临时目录里写一个 `结果.json`，当作第 7 步对 [07-检查结果](07-检查结果.md) 的 D0 做一维对照后的产物：

| 键 | 值 |
|---|---|
| 通过 | 真 |
| 迭代步数 | 100 |
| 进出口压差 | 150 |
| 多孔区压差 | 150 |
| 入口流量、出口流量 | 10、10 |
| 出口温度 | 580 |
| 吸热量 | 110000 |
| 多孔压降估算、出口温度估算 | 150、580 |
| 检查 | 六项，顺序是流量守恒、入口流量、监测值稳定、残差收敛、压差与一维解一致、出口温度与一维解一致；“通过”都为真；“说明”是任意非空文字 |

- “R0 四项”指只留前四项检查，其余不变，相当于不对照一维。
- 各测试点只写出与 R0 不同的地方。“某项不通过”指把该项的“通过”改成假，同时把最外层的“通过”改成假。只有 T8-27 故意让两者不一致。
- 用字典作输入时，内容与 `结果.json` 相同，另加第 7 步返回值多出的“算例目录”“结果路径”两项。

### 2.2 失败输入（“触发”类）

异常一律由真实的步骤函数抛出，测试不手写异常文字。这样前面步骤改了报错信息，第 8 步的测试能发现。

| 编号 | 怎么触发 | 异常 |
|---|---|---|
| F1 | `validate_boundary`，“面”里只有 walls | 校验错误 |
| F2 | `generate_mesh`，边界里某个面的类型写成不支持的值 | 标注错误 |
| F3 | `generate_case`，边界是只有“面”的字典，不给工况 | 工况错误 |
| F4 | `generate_mesh`，网格尺寸取 -1；横放圆柱取很粗的网格尺寸，使体积偏差超过 1% | 网格错误 |
| F5 | `generate_case`，步数取 0 | 算例错误 |
| F6 | `run_case`，用 [06-求解](06-求解.md) T6-17 的桩（`log.checkMesh` 里是 `Failed 2 mesh checks.`） | 求解错误 |
| F7 | `run_case`，分别用 T6-21（找不到 OpenFOAM）、T6-22（超时）、T6-31（找不到 docker）的做法 | 求解错误 |
| F8 | `run_case`，算例目录里没有 `Allrun` | 求解错误 |
| F9 | `run_case`，用 T6-19 的桩（`log.simpleFoam` 里有 `FOAM FATAL ERROR`） | 求解错误 |
| F10 | `check_result`，用 T7-29 的数据（没有一维估算值却要求对照） | 结果错误 |
| F11 | `check_result`，用 T7-25 的数据（`算例信息.json` 缺键） | 结果错误 |
| F12 | `check_result`，用 T7-26 的数据（缺监测数据） | 结果错误 |
| F13 | `check_result`，用 T7-44 的数据（没有 `log.simpleFoam`；残差是 nan） | 结果错误 |

- F10–F13 依赖第 7 步的实现。

### 2.3 输入与产物

- 输入有三种形式：第 7 步的返回值（字典）；算例目录路径（读里面的 `结果.json`）；第 2–7 步抛出的异常对象。
- 没有产物：不写文件，不改传入的字典和异常，不改算例目录。这一点与第 3 步相同。
- 返回值至少有：

| 键 | 含义 |
|---|---|
| 结论 | “通过”或“返工” |
| 回到步骤 | 步骤编号的列表，从小到大，不重复。通过时为空 |
| 对照一维 | 结论里含不含一维对照。输入是六项检查时为真，四项检查或异常时为假 |
| 原因 | 列表，每项有“现象”“回到步骤”“处理”“说明”。通过时为空 |

- “原因”里每一项的“回到步骤”按 2.4 的表给，顺序也按表（先试哪一步写在前面）。最外层的“回到步骤”是各原因的并集。
- “说明”照抄来源：检查不通过时抄 `结果.json` 里该项的“说明”，报错时抄异常信息。第 8 步不重新算数。

### 2.4 判定约定

第 7 步检查不通过时：

| 不通过的检查项 | 回到步骤 | 处理 |
|---|---|---|
| 流量守恒 | 5、4 | 按原因增加求解步数，或加密网格后重跑 |
| 监测值稳定 | 5、4 | 同上 |
| 残差收敛 | 5、4 | 同上 |
| 入口流量 | 2、4 | 先核对入口面的标注和入口速度，再加密网格 |
| 压差与一维解一致 | 2、4 | 先核对多孔体、流向和一维估算是否适用，再检查网格 |
| 出口温度与一维解一致 | 2、4 | 同上 |

第 2–7 步报错时，先看异常的类，同一类里再按表中从上到下的顺序看信息里的关键字：

| 异常 | 信息里的关键字 | 回到步骤 | 处理 |
|---|---|---|---|
| 校验错误 | 不看 | 2 | 在标注里指定面编号 |
| 标注错误 | 不看 | 2 | 改标注后重跑 |
| 工况错误 | 不看 | 2 | 改工况后重跑 |
| 网格错误 | 不看 | 4 | 减小网格尺寸，或修几何 |
| 算例错误 | 不看 | 5 | 按异常信息改输入后重写算例 |
| 求解错误 | `checkMesh 不通过` | 4 | 减小网格尺寸，或修几何 |
| 求解错误 | `找不到 docker`、`环境里找不到 OpenFOAM`、`超时`、`启动不了` | 6 | 修好环境或加大时限后重跑第 6 步，算例不用改 |
| 求解错误 | `第 5 步` | 5 | 重新写算例 |
| 求解错误 | 其余 | 5、4 | 先查算例设置和步数，再检查网格 |
| 结果错误 | `一维估算` | 7 | 不做一维对照，仅执行四项基本检查 |
| 结果错误 | `第 5 步` | 5 | 重新写算例 |
| 结果错误 | `残差` | 6 | 重新求解 |
| 结果错误 | `监测量` | 6 | 重新求解 |
| 结果错误 | 其余 | 5 | 重新写算例 |

- “通过”要同时满足：最外层“通过”为真；“检查”恰好是 [07-检查结果](07-检查结果.md) 2.4 规定的四项或六项，顺序一致；每一项“通过”都为真。
- “返工”：最外层“通过”为假，且至少有一项“通过”为假。每个不通过的检查项对应一条原因，顺序与“检查”里的顺序相同。通过的检查项不出现在原因里。
- 每一项都要判，不能遇到第一项不通过就停。
- 报错时原因恰好一条，“现象”里写出异常的类名。
- “不能判定”的情况：算例目录不存在；目录里没有 `结果.json`；`结果.json` 读不了；缺“通过”或“检查”；“通过”不是布尔值；“检查”不是四项或六项、顺序不对、项目名不认识或重复；某一项缺“项目”或“通过”；最外层“通过”与各项不一致；输入既不是字典、路径，也不是上表列出的异常。
- 不一致不能猜：最外层为真但有一项为假，或最外层为假但各项都为真，都报错。既不当通过，也不当返工。
- 不认识的异常（如 `KeyError`、普通的 `ValueError`）是程序出错，不是流程失败，报错并说明不是第 2–7 步的异常。
- 结论只由输入决定：没有时间戳，不读日志和监测数据，不看文件修改时间。
- 返回值能直接写成 JSON，里面没有 NaN 和 Infinity。

## 4. 完成标准

- T8-01 至 T8-39 全部通过。“OF”类测试点必须实际跑过，跳过不算。
- 3.2、3.3 的用例不能报错，3.4 的用例不能给出结论，两类不能混。
- 2.4 两张表的每一行至少被一个测试点覆盖。
- 端到端测试延伸到第 8 步：第 1 步生成的 S1–S3 经第 2–7 步后（步数用默认值，不对照一维），结论都是“通过”。S1 再做一次一维对照，结论仍是“通过”。
- 第 8 步的测试不重复验证六项检查的阈值，那是第 7 步的事。
- CI 里“造数”“触发”类直接跑，“OF”类用容器方式跑，不允许跳过。第 8 步实现之前不改 `pytest.yml`。
- 第 8 步实现后，先把 [工作流程](工作流程.md) 流程总览表里第 8 步的“仓库实现”一栏和第 4 节开头的说明改掉，再把本文纳入测试。

## 5. 已定事项

下面几项工作流程里没有写明，现在定下来。实现时按这里做，要改先改本文。

| 事项 | 决定 | 依据 |
|---|---|---|
| 接口形式 | `judge_result.py` 里的 `judge_result(输入)`。输入是第 7 步的返回值、算例目录，或第 2–7 步抛出的异常。能判定就返回字典，不能判定抛 `判定错误`。命令行是 `python judge_result.py 算例目录`，通过返回 0，返工或不能判定返回 1，用法不对返回 2。测试放在 `tests/test_judge_result.py` | 与 `check_result.py` 的约定一致 |
| 自动返工 | 不做。第 8 步只给结论 | 工作流程第 4 节写明自动回退尚未实现，表里是人工排查指引 |
| 产物 | 只有返回值，不写文件 | 与第 3 步相同。第 2–4 步报错时还没有算例目录，没有地方写 |
| 检查不通过的回退规则 | 按 2.4 第一张表 | 工作流程第 4 节 |
| 报错的回退规则 | 按 2.4 第二张表，先看异常的类，再看关键字 | 关键字取自 `run_case.py` 现有的报错信息 |
| 多项不通过 | 每项一条原因，步骤取并集 | 第 7 步“每一项都要算”就是为了这里能逐项判 |
| “回到步骤”的顺序 | 最外层从小到大；每条原因里按工作流程第 4 节写的先后 | 最外层给 CI 和脚本读，原因给人看 |
| “通过”怎么认 | 最外层“通过”与各项都为真才算，不一致就报错 | `结果.json` 是文件，可能被改过或写坏 |
| 说明文字 | 照抄，不重算 | 第 8 步不读监测数据 |
| 不认识的异常 | 报错，不当成返工 | 程序出错和流程失败要分开 |
| 测试怎么分 | 规则全用“造数”“触发”测，“OF”只测真实算例能走通 | 与第 7 步的分法一致 |

## 7. 水侧耦合的附加项

认四种检查组合：四项、六项、七项（四项 + 水侧稳定、热平衡、水未沸腾）、十项（七项 + 两项一维 + 水出口温度与一维解一致）。水侧稳定、热平衡不通过回到第 5、4 步（加步数或加密网格）；水未沸腾不通过回到第 2 步（改水流量或水入口温度，两相超出本流程）；水出口温度与一维解不一致回到第 2、4 步。
